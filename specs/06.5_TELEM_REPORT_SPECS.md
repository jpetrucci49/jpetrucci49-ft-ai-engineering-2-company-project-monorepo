## 1. Constraints (read first)

### 1.1 Cycle (mandatory)

```text
load (SQL) → refine (Pandas) → convert types → group → aggregate → serve
```

Two non-negotiables:

1. **The endpoint does not calculate metrics.** It resolves the date window, checks the cache, and calls the pipeline. Metric math lives in `analysis.py` only.
2. **Convert `timestamp` to `datetime` before any `groupby`.** Use `pd.to_datetime(..., utc=True)`. Grouping on date-looking strings produces wrong buckets and no exception.

### 1.2 Where each filter belongs

| Criterion | Layer | How |
| --- | --- | --- |
| `timestamp` range (`start_date` / `end_date`) | **SQL** | `WHERE timestamp >= :start AND timestamp < :end` — **inclusive start, exclusive end**, UTC |
| `event_type` (one or many) | **SQL** | `= :type` or `IN (...)`. Ratio metrics load **every type they need** in **one** query |
| `tags` dimensions (`route_template`, `route`, …) | **Pandas** | Extract from `tags`, drop rows where that dimension is null, then `groupby`. Segment **all** values — do not SQL-filter to a single endpoint |
| Derived flags (`is_error`, rates) | **Pandas** | Add columns after load, then `.agg()` / vectorised division |
| Optional extra row filters | **Pandas** (default) | After extract. SQL `tags->>'…'` push-down is optional, not required |

**Load** — only the rows that metric needs (`timestamp` window ± `event_type`). Never `SELECT` the whole table.

**Refine** — extract `tags`, drop null dimensions, metric-specific row filters. This does **not** replace SQL time / type filters.

**Date window ownership** — the **endpoint** computes the default (last 7 days UTC) and passes `start_date` / `end_date` into every metric function. Functions apply that window **once in SQL**. Do not re-apply “last 7 days” in Pandas.

### 1.3 Technical vs business

Answer: is the system healthy? Event volume, error rate, latency, which types dominate, login failure rate.

**Forbidden** as report metrics: inbound/outbound *counts as sales*, conversion rates, revenue, stock as a purchasing KPI, clinic league tables. Those wait for Data Pipelines.

Inventory `event_type`s may still appear in `events_per_day` as **volume** (what the platform emitted). Do not turn them into a business scorecard.

## 2. Phase 1 — analysis pipeline

### 2.1 Shared load (`analysis.py`)

One helper used by every metric. Signature idea:

```python
def load_events(
    session: Session,
    start: datetime,
    end: datetime,
    event_types: Sequence[str] | None = None,
) -> pd.DataFrame:
    ...
```

SQL (SQLModel / SQLAlchemy on the **same** `get_db()` engine — one pool):

- Always: `TelemetryEventRow.timestamp >= start` and `< end`
- If `event_types` is a non-empty sequence: `event_type IN event_types`
- If `event_types` is `None`: all types **in that window only** (needed for volume and error-rate denominators)

Select only: `timestamp`, `event_type`, `level`, `value`, `tags`.

Build the DataFrame from those rows (`pd.DataFrame.from_records` / equivalent). **Do not** `pd.read_sql` of `SELECT * FROM telemetry_events`.

Immediately after a non-empty load, **before refine/groupby**:

```python
frame["timestamp"] = pd.to_datetime(frame["timestamp"], utc=True)
```

Empty load → empty DataFrame with those columns (metrics return `[]`).

`tags` is already a `dict` from the ORM (Postgres JSONB / SQLite JSON). Extract with Pandas (`series.map` / `.apply` that returns a Series, or `pd.json_normalize` on a list of dicts). No Python `for` loops over rows to compute aggregates.

### 2.2 Metric functions

Each function:

- Arguments: `session`, `start: datetime`, `end: datetime` (timezone-aware UTC). **No** default window inside the function.
- Independent and side-effect free: same args → same result; no module-level mutation; do not write the cache here.
- SQL load as in §1.2 / §2.1 → refine → `pd.to_datetime` (if not already done in load) → `groupby` → `.count()` / `.sum()` / `.mean()` / `.agg()` → `.reset_index().to_dict(orient="records")`.
- JSON-safe values: `date` as `YYYY-MM-DD` strings; counts as `int`; rates / averages as `float`. Cast off NumPy scalars (`int(x)`, `float(x)`).
- Empty input → `[]`, not `null`, not 500.
- **No** `for` / `iterrows` to calculate metrics.

#### `events_per_day(session, start, end) -> list[dict]`

**Question:** which events fire, and how often, each UTC day?

- SQL: window only (`event_types=None`).
- Refine: none required.
- Group: UTC calendar day **and** `event_type`.
- Aggregate: `.size()` / `.count()` → `count`.
- Records: `{ "date": "YYYY-MM-DD", "event_type": "...", "count": N }` sorted by `date`, then `event_type`.

#### `error_rate_by_type(session, start, end) -> list[dict]`

**Question:** of events we stored, what share are `level='error'`, by day and type? (Temporal — not one lifetime percentage.)

- SQL: window only (need the denominator).
- Refine: `is_error = (level == "error")` as a 0/1 column (vectorised).
- Group: UTC day **and** `event_type`.
- Aggregate: `total = count`, `errors = sum(is_error)`, `rate = errors / total` (0.0 when `total == 0`, vectorised — no Python `if` per row).
- Records: `{ "date", "event_type", "errors", "total", "rate" }`.

Do **not** treat `warn` as error.

#### `latency_by_day(session, start, end) -> list[dict]`

**Question:** how slow are API calls we already instrumented?

- SQL: window **and** `event_type IN ('api_latency_recorded')`.
- Refine: numeric latency = column `value` if present else `tags["duration_ms"]`. Drop rows where latency is null. Extract `route_template` from `tags`; drop rows where it is null (segment all routes, do not pre-filter one).
- Group: UTC day **and** `route_template`.
- Aggregate: `avg_ms = mean(latency)`, `count = count`.
- Records: `{ "date", "route_template", "avg_ms", "count" }`.

`web_vital_recorded` stays out of this function (different question). Do not invent latency from inventory `quantity`.

#### `auth_failure_rate(session, start, end) -> list[dict]`

**Question:** daily login failure rate (additional activity).

- SQL: window **and** `event_type IN ('login_failed', 'login_succeeded')` — **one** query.
- Refine: `is_failure = (event_type == "login_failed")` as 0/1.
- Group: UTC day.
- Aggregate: `failures = sum(is_failure)`, `attempts = count`, `rate = failures / attempts` (0.0 if no attempts that day).
- Records: `{ "date", "failures", "attempts", "rate" }`.

Days with no login events do **not** appear (do not invent a 7-day zero-filled calendar in Pandas).

### 2.3 Assembler (still not the endpoint)

```python
def build_report(session: Session, start: datetime, end: datetime) -> dict:
    return {
        "period": {"from": start.isoformat(), "to": end.isoformat()},
        "metrics": {
            "events_per_day": events_per_day(session, start, end),
            "error_rate_by_type": error_rate_by_type(session, start, end),
            "latency_by_day": latency_by_day(session, start, end),
            "auth_failure_rate": auth_failure_rate(session, start, end),
        },
    }
```

`build_report` only orchestrates. It does not parse query strings or own the 7-day default.

## 3. Phase 2 — `GET /telemetry/report`

Still the same FastAPI app / router. **Authenticated** (`Depends(get_current_user)`). Ingest stays public (`sendBeacon`). CORS unchanged.

### 3.1 Query params

Optional `start_date` and `end_date` (ISO 8601). Accept date-only (`2026-09-01`) as that UTC midnight, or full datetime with offset / `Z`.

If **both omitted**: `end = now(UTC)`, `start = end − 7 days`.

If **one omitted**: treat the omitted side as that default relative to the provided side (`end` default now; `start` default `end − 7d`). Keep this in **one** `resolve_report_period(...)` helper next to the router or in a tiny `telemetry/period.py` — not inside metric functions.

Invalid ISO → existing sanitised **400**. `start >= end` → **400** with a short field message.

Pass the resolved aware UTC datetimes into `build_report`.

### 3.2 Response

```json
{
  "period": { "from": "2026-08-26T14:03:00+00:00", "to": "2026-09-02T14:03:00+00:00" },
  "metrics": {
    "events_per_day": [{ "date": "2026-08-31", "event_type": "page_viewed", "count": 4 }],
    "error_rate_by_type": [{ "date": "2026-08-31", "event_type": "frontend_error_uncaught", "errors": 1, "total": 1, "rate": 1.0 }],
    "latency_by_day": [{ "date": "2026-08-31", "route_template": "/api/inventory/products", "avg_ms": 42.0, "count": 3 }],
    "auth_failure_rate": [{ "date": "2026-08-31", "failures": 1, "attempts": 4, "rate": 0.25 }]
  }
}
```

Pydantic models on `models.py` (`TelemetryReportOut`, nested `period` / `metrics`). Do not rename metric keys.

`period.from` / `period.to` are the **resolved** bounds (ISO), not the raw query strings.

### 3.3 Cache (60s TTL)

`telemetry/cache.py`: process-local dict.

- Key: `(start.isoformat(), end.isoformat())` after resolve (so default “last 7 days” keys on the actual instants).
- Value: `{ "expires_at": monotonic or UTC datetime, "payload": report dict }`.
- TTL: **60 seconds**. Hit → return payload, **do not** call `build_report` / metric functions.
- Miss or expiry → `build_report`, store, return.

Endpoint shape:

```text
user = get_current_user
start, end = resolve_report_period(start_date, end_date)
cached = report_cache.get(start, end)
if cached is not None:
    return cached
payload = build_report(session, start, end)
report_cache.set(start, end, payload)
return payload
```

No Pandas import in `router.py`. No per-metric SQL in `router.py`.

Do not persist the cache to disk. Tests may `cache.clear()` in a fixture.

### 3.4 Endpoint tests

| Case | Expect |
| --- | --- |
| No token | **401** |
| No query params | 200; `period.to − period.from` ≈ 7 days; metrics keys all present |
| Explicit window | Metrics only include seeded rows inside `[start, end)` |
| Same window twice within 60s | `build_report` invoked **once** (monkeypatch / call counter) |
| After TTL | Second call recomputes (freeze time or set TTL=0 in test) |
| Bad `start_date` | 400 |
| `start_date` ≥ `end_date` | 400 |
| POST ingest still 200 / unauthenticated | Existing `test_telemetry.py` must keep passing |
