# SPECS — Milestone 5.5: Inventory Management with ORM & Dual Database

Implementation specification for the HealthCore **medical supply inventory API** — dual-database backend with SQLModel on Supabase PostgreSQL and existing TinyDB authentication. Build exactly what is described below.

**Prerequisite:** M7 JWT auth (`auth/dependencies.py`, `get_current_user`), M12 error-handling patterns (sanitized validation errors, safe 500 responses).  
**Authoritative domain data:** [`context/05.5_CONTEXT.md`](../context/05.5_CONTEXT.md) — entity names, fields, business rules, seed records, acceptance checks.

**Out of scope:** Frontend UI, BFF routes, clinic master data, HIPAA/PHI handling (inventory is operational data; all routes still require authentication).

---

## 1. Objective

Introduce a **dual-database** FastAPI backend:

| Store | Technology | Data |
| --- | --- | --- |
| **Auth** | TinyDB (existing) | Users, profiles, password-reset tokens |
| **Inventory** | Supabase PostgreSQL via SQLModel | `MedicalSupply`, `SupplyDelivery`, `SupplyConsumption` |

The application maintains **two deliberate connections**. Auth lookups never hit PostgreSQL; inventory queries never read TinyDB user tables. Every inventory write records the authenticated TinyDB user id in `user_uuid`.

**Stock invariant:** `current_stock` is **computed**, never stored or directly mutable. The only way to change inventory is by registering a **supply delivery** (inbound) or **supply consumption** (outbound).

All inventory HTTP endpoints live under the **`/inventory`** router prefix.

Context documents a flat `services/` tree; in this monorepo, implement under **`services/api/`** alongside existing modules:

```text
services/api/
  app/
    main.py                      ← mount inventory router; run create_all in lifespan
  auth/                          ← unchanged (TinyDB)
  database.py                    ← unchanged (supplier TinyDB)
  inventory/
    __init__.py
    database.py                  ← SQLModel engine + get_db() session dependency
    models.py                    ← MedicalSupply, SupplyDelivery, SupplyConsumption
    schemas.py                   ← Request/response Pydantic models (separate classes)
    service.py                   ← current_stock computation, order validation

  .env.example                   ← SUPABASE_DATABASE_URL (or equivalent)
  pyproject.toml                 ← add sqlmodel + PostgreSQL driver (§5)
  tests/
    test_inventory.py
    conftest.py                  ← extend with test PostgreSQL session fixture
```

Register the router in `app/main.py`:

```python
from inventory.router import router as inventory_router

app.include_router(inventory_router)
```

No `/api` prefix on this router — paths are exactly `/inventory/...` per context.

## 6. Database Configuration

### 6.1 Environment

Add to `services/api/.env.example` and document in `services/api/README.md`:

| Variable | Required | Purpose |
| --- | --- | --- |
| `SUPABASE_DATABASE_URL` | **Yes** (for inventory) | PostgreSQL connection string from Supabase (Session mode or direct). Never hardcode credentials. |

Example shape (values from Supabase dashboard):

```bash
SUPABASE_DATABASE_URL=postgresql://postgres.[project-ref]:[password]@aws-0-[region].pooler.supabase.com:6543/postgres
```

Load via existing config pattern (`os.environ` or `pydantic-settings` if already used). Fail fast at startup with a clear message if the URL is missing when inventory routes are enabled.

### 6.2 Dual connections in `inventory/database.py`

| Connection | Initialisation |
| --- | --- |
| TinyDB (auth) | **Existing** — `auth/database.py`; do not modify for this milestone |
| TinyDB (suppliers/incidents) | **Existing** — `database.py`, `incidents_database.py` |
| PostgreSQL | **New** — `create_engine(SUPABASE_DATABASE_URL)` + `sessionmaker` |

Implement:

```python
def get_db() -> Generator[Session, None, None]:
    session = SessionLocal()
    try:
        yield session
    finally:
        session.close()
```

- One session per request via `Depends(get_db)`.
- No module-level mutable session shared across requests.
- Name the dependency `get_db` in the inventory module; if importing both TinyDB and SQLModel helpers in one file, alias explicitly (e.g. `get_inventory_db`).

### 6.3 Schema initialisation

In application **lifespan** (or startup event), after engine creation:

```python
SQLModel.metadata.create_all(engine)
```

> **Development only:** `create_all()` is acceptable for local and learning environments. **Never** run `create_all()` against a shared or production database — use versioned migrations (e.g. Alembic) in production.

## 7. ORM Models — `inventory/models.py`

Define SQLModel table classes using names and fields from [`context/05.5_CONTEXT.md`](../context/05.5_CONTEXT.md). Use `SQLModel, table=True`.

### 7.1 `MedicalSupply`

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `int` | Primary key, auto-increment |
| `name` | `str` | Required |
| `sku` | `str` | Internal catalogue code; **unique** |
| `category` | `str` | One of: `ppe`, `wound_care`, `diagnostics`, `medications`, `consumables` |
| `unit` | `str` | e.g. `box`, `unit`, `pack`, `vial` |
| `country` | `str` | `"US"` or `"UK"` — regulatory jurisdiction |

**Do not store `current_stock`** on this table.

### 7.2 `SupplyDelivery` (inbound)

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `int` | Primary key, auto-increment |
| `supply_id` | `int` | FK → `MedicalSupply.id` |
| `quantity` | `int` | Units received; must be > 0 |
| `vendor_name` | `str` | Required |
| `clinic_id` | `int` | Receiving clinic **1–12**; not a FK |
| `created_at` | `datetime` | UTC; set on insert |
| `user_uuid` | `str` | TinyDB user id as string (from JWT); no Supabase user table |

Relationship: `MedicalSupply` ↔ `SupplyDelivery` via `supply_id`.

### 7.3 `SupplyConsumption` (outbound)

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `int` | Primary key, auto-increment |
| `supply_id` | `int` | FK → `MedicalSupply.id` |
| `quantity` | `int` | Units consumed; must be > 0 |
| `consumption_type` | `str` | `"clinical_use"` or `"expiry_waste"` only |
| `clinic_id` | `int` | Clinic **1–12**; not a FK |
| `created_at` | `datetime` | UTC; set on insert |
| `user_uuid` | `str` | TinyDB user id as string |

Relationship: `MedicalSupply` ↔ `SupplyConsumption` via `supply_id`.

### 7.4 ORM constraints

- `user_uuid` is populated from `str(current_user.id)` where `current_user` comes from `Depends(get_current_user)`.
- No `User` SQLModel table in PostgreSQL.
- US and UK supplies coexist in the same `MedicalSupply` table; `country` distinguishes jurisdiction.

## 8. Pydantic Schemas — `inventory/schemas.py`

**Separate file from ORM models.** Request and response types are standalone Pydantic `BaseModel` classes (or SQLModel schemas with `table=False` if preferred — but keep table models in `models.py` only).

### 8.1 Medical supply (product)

| Schema | Purpose |
| --- | --- |
| `MedicalSupplyCreate` | `POST /inventory/products` body — `name`, `sku`, `category`, `unit`, `country` |
| `MedicalSupplyResponse` | All supply fields + **`current_stock: int`** (computed at read time) |

Validate `category`, `country`, and positive quantities in schemas (field-specific messages per M12).

### 8.2 Inbound order

| Schema | Purpose |
| --- | --- |
| `SupplyDeliveryCreate` | `POST /inventory/orders/inbound` — `supply_id`, `quantity`, `vendor_name`, `clinic_id` |
| `SupplyDeliveryResponse` | Full delivery record including nested or embedded supply summary |

### 8.3 Outbound order

| Schema | Purpose |
| --- | --- |
| `SupplyConsumptionCreate` | `POST /inventory/orders/outbound` — `supply_id`, `quantity`, `consumption_type`, `clinic_id` |
| `SupplyConsumptionResponse` | Full consumption record |

Validate `consumption_type` with a `Literal["clinical_use", "expiry_waste"]` or enum; invalid values → **422** with clear field message.

### 8.4 Order list

| Schema | Purpose |
| --- | --- |
| `InventoryOrderResponse` | Unified list item for `GET /inventory/orders` |

Include a discriminator so clients can tell deliveries from consumptions, e.g.:

- `order_type: Literal["inbound", "outbound"]`
- Supply fields needed for display (`supply_id`, supply `name`, `sku` at minimum)
- `user_uuid`, `quantity`, `clinic_id`, `created_at`
- For outbound: `consumption_type`; for inbound: `vendor_name`

## 9. Business Rules — `inventory/service.py`

Implement stock logic in a service layer; routers stay thin.

### 9.1 `current_stock` computation

For each `MedicalSupply`:

```text
current_stock = SUM(SupplyDelivery.quantity) − SUM(SupplyConsumption.quantity)
```

- Computed at query time (SQL `SUM` subqueries or aggregate in Python after fetch).
- **Not** scoped by `clinic_id` — stock is **global per supply** across all clinics (per context).
- `clinic_id` on orders is metadata only for this milestone.
- Never persist `current_stock`; only include it on response schemas.

### 9.2 Product creation

- New supplies start with **zero stock**.
- Stock increases only via `SupplyDelivery` records.
- Reject duplicate `sku` → **400** or **409** with descriptive message.

### 9.3 Inbound orders

- Require authentication.
- Validate `supply_id` exists → else **404**.
- Validate `quantity > 0`, `clinic_id` in **1–12**.
- Set `user_uuid` from authenticated user; set `created_at` server-side.

### 9.4 Outbound orders

- Require authentication.
- Validate `supply_id` exists → else **404**.
- Validate `consumption_type` ∈ `{clinical_use, expiry_waste}`.
- Validate `quantity > 0`, `clinic_id` in **1–12**.
- **Before insert:** compute available stock for the supply. If `quantity > available`, reject with **400** and **exact message**:

```text
Insufficient stock for supply '{name}'. Available: {available}, requested: {quantity}.
```

Use the supply's `name` in the message. Do not persist the consumption row on failure.

### 9.5 Authentication

| Route | Auth |
| --- | --- |
| All `GET` inventory routes | **Required** — `Depends(get_current_user)` |
| All `POST` inventory routes | **Required** |

Unauthenticated requests → **401** with existing auth error constant (no credential leakage).

## 10. Inventory Router — `inventory/router.py`

```python
router = APIRouter(prefix="/inventory", tags=["inventory"])
```

Mount without an additional prefix in `app/main.py`.

### 10.1 Endpoints

| Method | Path | Handler behaviour |
| --- | --- | --- |
| `GET` | `/inventory/products` | List all `MedicalSupply` rows with computed `current_stock` |
| `POST` | `/inventory/products` | Create supply; auth required; returns supply with `current_stock: 0` |
| `GET` | `/inventory/products/{id}` | Single supply + `current_stock`; **404** if missing |
| `POST` | `/inventory/orders/inbound` | Create `SupplyDelivery`; auth required |
| `POST` | `/inventory/orders/outbound` | Create `SupplyConsumption`; auth required; enforce stock rule §9.4 |
| `GET` | `/inventory/orders` | List all deliveries and consumptions with supply data and `user_uuid` |

**URL naming:** Paths use `products` and `orders/inbound|outbound` per context; code entities remain `MedicalSupply`, `SupplyDelivery`, `SupplyConsumption`.

### 10.2 Error responses

| Condition | Status | Detail |
| --- | --- | --- |
| Missing/invalid token | 401 | Existing auth message |
| Validation error | 422 | M12-sanitized field-labelled messages |
| Insufficient stock | 400 | Exact message from §9.4 |
| Supply not found | 404 | `"Supply not found."` or equivalent |
| Duplicate SKU | 400/409 | Descriptive message |
| Unhandled server error | 500 | Generic message (M12) |

## 15. Architecture Diagram

```text
┌─────────────┐     Bearer JWT      ┌──────────────────────────────────────┐
│   Client    │ ──────────────────► │           FastAPI (services/api)      │
└─────────────┘                     │                                      │
                                    │  get_current_user ──► TinyDB (auth)  │
                                    │         │                            │
                                    │         └── user.id → user_uuid      │
                                    │                                      │
                                    │  get_db (inventory) ──► Supabase PG  │
                                    │         │                            │
                                    │         ├── MedicalSupply            │
                                    │         ├── SupplyDelivery           │
                                    │         └── SupplyConsumption        │
                                    └──────────────────────────────────────┘
```

**Stock flow:** `POST …/orders/inbound` inserts `SupplyDelivery` → stock ↑.  
`POST …/orders/outbound` validates then inserts `SupplyConsumption` → stock ↓.  
`GET …/products` never reads a stored stock column — always aggregates movements.
